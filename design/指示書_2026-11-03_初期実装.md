# Claude Code への指示書：初期実装（データ層〜ローカル版〜チューナー）

作成日：2026-11-03
準拠するルール：claude/rules.md v0.8（第19章の暫定規定を含む）
参照する設計文書：claude/decisions.md（2026-11-03 時点）、claude/data_characters.json、claude/data_special_citizens.json、claude/data_raid_cards.json、文明カード一覧_sample.md
対象の段階：実装の段階1〜4（データ層、ゲームロジックの骨格、効果、ローカル UI）と、チューナー（編集・試遊）
対象外：オンライン化（段階5）、ヴァリアント（段階6）、チューナーの検証機能（シミュレーション。balance-sim のエージェント作成後に別の指示書で扱う）

## 0. 前提

### 0-1. 設計文書の置き場

上記の設計文書は、ユーザーがリポジトリの `design/` に置く。Claude Code は `design/` を読むだけで、変更しない。設計文書と食い違う実装をしたくなった場合は、実装を止めて報告する。

### 0-2. 技術スタック

TypeScript（strict）＋ React ＋ Vite ＋ Vitest。配布は `vite-plugin-singlefile` による1枚の HTML。盤面の描画は SVG。受け入れ検査は Playwright。これ以外のライブラリは導入しない。必要になった場合は、導入前に理由を報告する。

### 0-3. 進め方

- 下記の5つのブランチを順に作業する。1つのブランチを完了条件まで終えたら作業を止め、成果（遊べる状態、または通るテスト）と、実装中に判断した点の一覧を報告する。ユーザーの確認を得てから `main` に取り込み、次のブランチに進む。
- rules.md に未定義箇所を見つけた場合、合法手・得点・勝敗に影響するものは実装を止めて列挙する。推測で補完しない。操作の簡便化など結果に影響しないものは、暫定の扱いを決めて進め、報告に含める。
- リポジトリ直下に `CLAUDE.md` を作る。構成・コマンド・守ること・既知の制約を書き、運用を変えたら更新する。
- コード内のコメントと文書は日本語の「である調」で書く。

### 0-4. 全ブランチ共通の完了条件

- `npm run typecheck`、`npm test`、`npm run build` がすべて通る。
- 単体テストの各ケースに、対応する rules.md のバージョンと条項番号をコメントで書く（例：`// rules.md v0.8 3-3-1-2`）。
- 失敗している状態で完了扱いにしない。

## 1. 数値をすべてデータに置く

調整の対象になりうる数値をコードに書かない。次を `src/data/` の型付きデータとして持ち、ゲームロジックはそれを読む。後で実装するチューナーは、ここにあるものを編集の対象とする。

- `params.json`：ルール本文の数値パラメータ。少なくとも次を含める。
  - プレイ人数ごとの準備（特別な市民カードの公開枚数、計画都市カードの公開枚数、場のボーナスタイル枚数）
  - 初期資源（2-2-1）、軍事レベル・インフラレベルの初期値
  - 通常ワーカーの上限の式の係数（3-3-1-2：基本5、住宅2軒ごとに+1、最大10）、臨時ワーカーの上限
  - 土地タイルのコスト（4-3）、開拓アクションの割引
  - 建物の上限（5-2-1）、建設コスト（5-3-1）、地形ボーナス（5-4-1）、建物の効果の数値（5-5）、最上位アクションの解放条件
  - 各アクションの通常・上位・最上位の内容（6-3）
  - 軍事レベル・インフラレベルの上限と到達報酬（7-1、8-1）、教練の超過得点
  - 襲撃の基本得点（7-5-1）
  - フリーアクションの資源変換（10-1-3）
  - 得点計算の換算表（第17章）
- `board_*.json`：個人ボード（地形配置、マスボーナス）
- `cards_civilization.json`、`cards_planned_city.json`、`cards_nature_park.json`、`special_citizens.json`、`characters.json`、`raid_cards.json`、`bonus_tiles.json`

各データには `provisional`（仮置きなら true）を持たせる。仮置きのデータは、画面上でも仮置きであることが分かる表示を付ける。

## 2. 仮置きデータの作り方

設計文書にない値は、次の規則で Claude Code が仮置きする。作った値はすべてデータファイルに残し、ブランチの報告で一覧にする。

### 2-1. 文明カード

- `design/文明カード一覧_sample.md` の 001〜042 の42枚を収録する。デッキはこの42枚とする（総枚数は未決のため）。
- 文言の扱い（decisions.md 1-1）：タグは配列で持つ。サンプルは全カード1タグである。011 の「生活レベル」はインフラレベルとして扱う。
- 仮置き：名称は「文明カード001」の形、プレイ条件と効果適用条件はなし、固有得点は全カード1点。
- 文言の解釈で迷うものは、次の扱いで仮置きし、報告に含める。
  - 「軍事力」（027、034、042 など）：軍事レベル。
  - 026「襲撃の撃退に必要な軍事力1につき1金」：そのラウンドの撃退ライン − 軍事レベル（0未満は0）。
  - 003「金を支払わずに建物を3軒まで建設」：建設コストのうち金だけを免除し、資材は支払う。
  - 006〜009「地形を無視して〜土地タイルを置く」：資材は支払わない（19-1-1）。配置は 4-2-1 の隣接に従う。

### 2-2. 個人ボード

- 5枚（4人プレイのドラフトで「プレイ人数より多い」を満たす数）を、シード付きの乱数で生成する。
- 地形の内訳は 2-1-5（水場7・山岳7・平原16・森林15）、E1・F1 は森林（2-1-7）。
- マスボーナス（4-4-4-2）：各ボード6マスに、次のいずれかを仮置きする。資材1、金2、文明カード1枚、軍事力トークン1。E1・F1 には置かない。

### 2-3. 計画都市カード

- 8枚を仮置きする。建物数は3〜5軒、形状は直線・折れ線・三角形などヘクスでつながった形とする。条件は 13-2-2 の3種類（土地種と建物種、土地種のみ、建物種のみ）を組み合わせる。
- 達成時の恩恵は、金3・資材2・文明カード1枚のいずれかを仮置きする。

### 2-4. 自然公園カード

- 8枚を仮置きする。各カードは3セットで、それぞれ2枚・3枚・4枚のセットとする。どのセットも森林を含む（14-1-4）。形状はヘクスでつながった形とする。

## 3. ブランチと作業内容

### 3-1. `feat/data-layer`（段階1：データ層）

- 第1章・第2章の方針で `src/data/` を作り、型を定義する。`design/` の JSON は文言をそのまま取り込み、文言の解釈（clarifications）も保持する。
- 盤面の座標と隣接（2-1-3、2-1-3-2、2-1-3-3）を `src/game/board.ts` に実装する。
- テスト：データの型検査、参照の整合（存在しない ID がない）、各個人ボードの地形の内訳、隣接の対称性と E1 の隣接（D1・E2・F1）。

### 3-2. `feat/game-core`（段階2：ゲームロジックの骨格）

- 選択待ちモデルを採用する。`createGame(config, seed)`、`getOptions(state)`、`applyMove(state, optionId)`、`isGameOver(state)`、`finalScores(state)` を公開する。手番の行動（アクションの選択、パス）も選択待ちの最初の選択として扱う。
- 乱数はシード付きの擬似乱数とし、内部状態を GameState に含める。`Math.random()` を使わない。GameState は JSON で直列化できる形に保つ。
- `src/game/history.ts` に `replay`、`isCheckpoint`、`undoLast` を持つ。チェックポイントは乱数の消費・非公開情報の公開・選択権の移動・フェイズの変化に加え、19-6-3（襲撃の判定、ドラフトの選択、ボーナスタイルの選択）とする。
- 実装する範囲：準備とドラフト（第2章、2-6-7 の一方向巡回、2-6-4-2）、ラウンドの進行（第12章、12-0-4〜12-0-7）、パスとボーナスタイル（第11章、19-4-2）、ワーカーの配置と占有（第6章 6-1・6-2）、開拓・建築（第4章・第5章）、全10アクション（6-3）、フリーアクション（第10章）、軍事とインフラのトラック（第7章・第8章）、襲撃（7-3〜7-6、19-3）、ゲーム終了と得点計算（第17章、17-0-2、17-0-3）、同点判定。
- 部分実行とコストの原則（6-1-6、6-1-6-2、6-1-7、4-4-1-2、16-2-4〜16-2-6）と、「〜した時」の1単位ごとの発動（16-1-4、16-1-5）を共通の仕組みとして作る。
- 「任意の順番」は、資源・得点を得るだけの組み合わせなら尋ねずに処理し、配置や選択を含むときだけ尋ねる（decisions.md 3-4）。
- 得点はゲーム中は1本のトラックで記録し、得点源の区分（評価軸または「その他」）を出来事として残して、終了時の内訳に使う（17-0-3）。
- テスト：rules.md の各条項に対応する単体テスト。性質テストとして、乱択プレイアウト（3人・4人、各100局以上）で「合法手が存在しない状態に陥らない」「規定手数内に終局する」を確かめる。

### 3-3. `feat/effects`（段階3：効果）

- 効果は共通の小さな命令セットの組み合わせで表し、カードごとに個別のコードを書かない。命令セットは、文明カード 001〜042、特別な市民カード 01〜20、キャラクター10種、計画都市の恩恵、マスボーナスを書ける最小のものとする。設計方針（命令の一覧と引数）を実装前に報告する。
- 常時効果（9-2-9、特別な市民カードの常時、キャラクターの固有効果）は、出来事への反応として同じ命令セットで書く。
- キャラクターの暫定規定（19-5-1〜19-5-7）、特別な市民カードの規定（6-2-4、6-2-5、9-3-2-2、19-2-11、19-4-3）、計画都市（第13章、19-1-6、19-4-7、19-5-3）、自然公園（第14章、19-1-5、19-4-8）を実装する。
- テスト：命令ごとの単体テスト、カード・キャラクターの種別ごとのテスト、性質テストの再実行。

### 3-4. `feat/local-ui`（段階4：ローカル UI）

- 1台で交代して遊べる版を作る。画面の持ち主は選択待ちのプレイヤーに自動で合わせ、他のプレイヤーの手札の内容は画面にも DOM にも出さない（19-6-1）。
- 盤面は SVG で描く。`src/game/` は `targets.ts`（`targetOf`）、`explain.ts`（`explain`）、`queries.ts`（割引後のコスト、配置可能なマスなど）、`GameState.events` を公開し、UI は判定をこれだけに頼る。UI でルールを再実装しない。
- 取り消しは `history.ts` の `undoLast` を使う。
- 見た目は仮でよい（世界観・ビジュアルは未着手）。仮置きデータには仮置きの表示を付ける。
- 受け入れ検査：Playwright の自動対戦が、盤面の所作だけで1局を最後まで打ち切ること。安全網に落ちた合法手・画面のはみ出し・他人の手札の DOM への漏れ・ページのエラーが0件であること。自動対戦は取り消しを選ばない。

### 3-5. `feat/tuner`（チューナー：編集と試遊）

- `tools/tuner/` に置くローカルのページとし、`npm run tuner` で起動する。配布用ビルドには含めない。
- 編集：`src/data/` の全データ（`params.json`、カード、キャラクター、ボード、ボーナスタイル、襲撃カード）を種別ごとに一覧し、各項目をフォームで編集できる。効果は命令と引数の単位で編集でき、命令セットにない記述はできない。個人ボードは地形とマスボーナスをマスごとに編集できる。
- 編集は作業中の写し（調整案）に対して行い、元データは変更しない。調整案は名前・作成日・変更点の一覧（元の値 → 新しい値）を持ち、JSON として保存・読み込みできる。
- 保存前に、型と参照の検査（存在しない ID、範囲外の値、地形の内訳の不一致など）を行う。
- 試遊：調整案を適用した状態でローカル版を起動し、人が遊べる。
- 書き出し：採用した調整案を `src/data/` に差分として書き戻す。書き戻しは `npm run tuner` の開発サーバーが受ける。あわせて変更点の一覧を Markdown で出力する（ユーザーが claude/tuning_log.md に転記する）。
- 検証（シミュレーションによる比較）は本指示書の対象外とする。画面上に枠だけを用意してよい。
- テスト：調整案の作成・差分・保存と読み込み・検査の単体テスト。調整案を適用したゲームが性質テストを通ること。

## 4. 報告に含めるもの

各ブランチの完了時に、次を報告する。

- 完了条件（型検査・テスト・ビルド、該当する場合は受け入れ検査）の結果
- 仮置きしたデータの一覧
- 実装中に判断した点（結果に影響しない UX 上の判断）
- rules.md の未定義箇所として止めた点
- 環境固有の落とし穴（引き継ぎ書に残すため）
